1. Give the play queue its own module

Strong in-process

lib/player/states/player.dart · lib/player/states/tv_player_controls.dart · lib/player/views/components/mini_player_controls.dart

Before · queue spread through PlayerCubit (1065 lines)

five fields kept in step by convention

videosofflineVideosplayedVideosplayQueuecurrentlyPlaying ×2

about 11 methods, mixed with IO and throttles

queueVideosplayNext_playNextNowplayPreviousskipToVideoremoveVideoFromQueueonQueueReordergeneratePlayQueue…

online/offline branch repeated 14×

TV playFromQueue skips played/next bookkeeping

view calls toggleShuffle() then generatePlayQueue()

After · one deep, pure module

PlayerCubit asks, then performs the switch

Play queue

small interface: add, remove, reorder, advance, go back, jump to

one item listplayed / upcoming splitrepeat policyshuffle policywhat plays next

No db, no service, no timers. Phone and TV go through the same entry.

Problem. Queue rules are maintained across five state fields and about eleven methods, so the phone and TV paths have already diverged.

Solution. Move the item list, the played / upcoming split, and the repeat and shuffle rules into one synchronous module that PlayerCubit consults.

  • Queue tests need no platform fakes
  • One list instead of two
  • TV and phone share bookkeeping
  • Shuffle regenerates itself

Problem. The "watched" threshold is written three times, and resume lives in each engine, so proxied audio never resumes.

Solution. One module decides when to save, where to resume, when a video counts as watched, and when to jump a SponsorBlock segment, with the store passed in.

  • Threshold defined once
  • Audio and video resume identically
  • Skip rule testable without time
  • Uses existing in-memory db

Two things the agent flagged that you should confirm are intended: offline videos never save position (player.dart 277-278), and the skip adds 2 s where the comment says 1 (367, 374).

3. Narrow the player-engine seam

Worth exploring ports & adapters

lib/player/states/interfaces/media_player.dart · video_player.dart · audio_player.dart · tv_player_settings.dart · views/components/{video_player,audio_player}.dart

Before · interface as wide as the adapters

MediaPlayerCubit interface: about 34 members

stubbed by the audio adapter: about 12 (one throws)

never called through the interface: 6

commands go down through a BlocListener in the view
events come up by direct player.setEvent calls (26 sites)
TvPlayerSettingsCubit drives the concrete video controller

After · thin adapters behind a small interface

Playback source resolution

online or offline fileproxy and headersstart positionremembered speed
video adapter
river_player
audio adapter
just_audio

Track selection becomes optional for an adapter rather than stubbed. Commands and events travel one route.

Problem. Both adapters repeat server, proxy, header and speed handling, and the interface forces the audio adapter to stub a third of it.

Solution. Pull source resolution out of the adapters and shrink the interface to what both engines really do.

  • No throwing stubs
  • Proxy logic written once
  • Adapters swap without the view
  • TV settings use the seam

This is the largest of the five and touches the hottest files. It gets much cheaper after candidates 1 and 2, which remove what the adapters reach back into PlayerCubit for.

4. Replace the stubbed second db adapter with a background store

Worth exploring local-substitutable

lib/utils/interfaces/db.dart · lib/utils/file_db.dart · lib/utils/sembast_sqflite_database.dart · lib/workmanager.dart · lib/service.dart 235, 529, 554, 773 · lib/notifications/**

After · two honest modules

App database

one adapter (Sembast), in-memory variant for tests, as today

Background store

what the workmanager isolate can read and write

current serverlocalelast-seen markersnotification subscriptions

Fetching a channel no longer writes a notification marker as a side effect; the caller that knows the user viewed it does.

Problem. FileDB claims the whole db interface but implements five members, so any code running in the background isolate can throw at runtime.

Solution. Stop FileDB posing as a db adapter and name it for what it is: the small store shared with the background isolate.

  • 33 throwing stubs deleted
  • Background code cannot hit them
  • Notification state has one owner
  • Service stops writing storage

Inferred, not confirmed: that the file store exists because the Sembast database cannot be opened from the workmanager isolate. If that reason is wrong, this candidate changes shape. I did not read file_db.dart or the notification cubits in full.

Problem. The TV screen builds its own play list inside the widget and ignores two settings the phone path honours.

Solution. Let the feature cubit decide which videos play and leave each tree to layout and focus handling.

  • Settings apply on every device
  • Rule testable without widgets
  • One place to change

Rated speculative because I verified one instance of drift, not a pattern. Supporting counts: views call context.read 182 times, reach service from 10 view files and db from 7, and device-type checks appear 42 times (33 in views). Share, add-to-playlist and download actions have no TV counterpart at all, which may be deliberate. The TV tree's separate layout and D-pad handling look like they should stay separate.

Top recommendation

1. Give the play queue its own module

It sits in the most-changed file, it is pure logic with no platform dependency, and it would give the player its first real tests without standing up audio session or media handler fakes. It also shrinks PlayerCubit enough to make candidates 2 and 3 tractable.
